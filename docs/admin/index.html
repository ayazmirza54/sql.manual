#Users, roles & privileges

SQL's DCL is small: GRANT and REVOKE. Everything else is vendor-specific.

::: tip Grant future objects too GRANT … ON ALL TABLES applies only to tables that exist now. A table created tomorrow is not covered:

:::

MySQL / MariaDBUsers are 'name'@'host'; roles since 8.0

OracleUsers == schemas; system vs object privileges; roles

#Connection management

Connections are expensive: each one costs a backend process (PostgreSQL) or thread (MySQL) plus memory, and the working set of idle connections still competes for cache.

#Backup & restore

Two kinds, and you need both:

  • Logical — a dump of SQL statements or a portable archive. Restores anywhere, slow for large data, no point-in-time recovery on its own.
  • Physical — a byte-level copy of the data files plus the WAL/redo stream. Fast, exact, enables point-in-time recovery (PITR), but restores only to the same major version and platform.

::: danger An untested backup is not a backup Restore drills belong on a schedule, not in a runbook nobody has run. Record the actual RTO (how long a restore takes) and RPO (how much data a failure loses) by measuring them. The three most common discoveries: the backup never included the schema, the restore takes eleven hours, and nobody has the decryption key. :::

::: warn Read replicas are eventually consistent A write committed on the primary is not immediately visible on a replica. "Save then redirect to the detail page" reads stale data and looks like a lost write. Route read-after-write to the primary, or wait for the replica's LSN to catch up. :::

#Monitoring

What to watch, in rough priority order:

  1. Replication lag — seconds and bytes behind.
  2. Connection count vs the limit, and how many are idle-in-transaction.
  3. Cache hit ratio — below ~95% on OLTP means the working set no longer fits.
  4. Longest-running query / transaction age.
  5. Lock waits and deadlock rate.
  6. Disk free, plus WAL/binlog/undo growth (a stuck replication slot fills the disk and stops the primary).
  7. Bloat / fragmentation, and time since last vacuum/analyze.
  8. Checkpoint frequency and I/O saturation.

#Partitioning

Split one logical table into physical pieces so the engine reads only the relevant ones and maintenance operates per piece.

SchemeSplit byGood for
RangeOrdered value, usually a dateTime-series, retention policies
ListEnumerated valueTenant, region, status
HashHash of a keyEven distribution when there is no natural range
CompositeRange then hash/listLarge multi-tenant time-series

::: warn Partitioning is not a general speedup It helps only when queries filter on the partition key so the planner can prune. Add a partition key most queries do not use and every query fans out across every partition, which is slower than the unpartitioned table. Its real wins are cheap retention (drop a partition instead of a mass DELETE) and per-partition maintenance. :::

::: tip HA is not backup A replica faithfully replicates DROP TABLE orders in milliseconds. Replication protects against hardware failure; backups protect against mistakes and corruption. You need both, and the backups must live somewhere the primary's credentials cannot reach. :::
