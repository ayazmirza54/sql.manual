Indexes

Index structures (B-tree, hash, GiST, GIN, BRIN, columnstore), composite and covering indexes, selectivity, and how to tell whether an index is doing anything.

An index is a redundant, ordered copy of some columns that lets the engine find rows without reading the whole table. Every index makes reads faster and writes slower — that trade-off is the whole subject.

#The structures

TypeAnswersEngines
B-tree=, <, >, BETWEEN, IN, prefix LIKE 'a%', ORDER BY, MIN/MAXEverywhere; the default

GINElements inside a composite value: array items, JSONB keys, text lexemesPostgreSQL
BRINHuge, naturally-ordered tables — stores min/max per block rangePostgreSQL
SP-GiSTNon-balanced structures: quadtrees, tries, IP prefixesPostgreSQL
BitmapLow-cardinality columns in a read-mostly warehouseOracle, Db2
ColumnstoreAnalytical scans and aggregation over many rowsSQL Server, Oracle (in-memory), Synapse
Full-textWord and phrase matching with rankingAll (different names)

::: note Columnar engines do not have indexes in the usual sense Redshift, Snowflake, BigQuery and Databricks have no CREATE INDEX for scan pruning. Performance comes from sort keys / clustering keys / partitioning, which physically order the data so block-level min/max metadata can skip whole ranges. Advice written for PostgreSQL does not transfer — see each engine's page. :::

#Creating indexes

#Composite indexes and column order

An index on (a, b, c) is usable for a leading prefix of its columns — a, (a, b), (a, b, c) — and not for b alone or (b, c).

Ordering rule: equality columns first, then the range/sort column last.

::: tip A composite index replaces the single-column index on its first column (a, b) makes a separate index on (a) redundant — drop it. It does not replace an index on (b). :::

#Covering indexes and index-only scans

If an index contains every column a query touches, the engine can answer from the index alone and never read the table.

::: warn PostgreSQL index-only scans need a visible page PostgreSQL must still check row visibility in the visibility map. If the table has not been vacuumed recently, Heap Fetches will be high and the "index-only" scan is not much faster than a normal one. Keep autovacuum healthy. :::

#Partial / filtered indexes

Index only the rows you query. Smaller index, cheaper writes, and it can enforce conditional uniqueness.

#Selectivity — when an index is worth using

Selectivity is the fraction of rows a predicate keeps. An index helps when that fraction is small; below roughly 5–20% of the table (engine and row-width dependent) a sequential scan is genuinely faster, because random I/O per row costs more than reading everything in order.

::: note "The index is not being used" is often correct behaviour If the planner estimates the predicate matches most of the table, ignoring the index is the right call. Before forcing it, check whether the estimate is wrong — stale statistics, a correlated multi-column predicate, or a data skew the planner cannot see. ANALYZE first. :::

::: danger Implicit casts silently disable indexes If user_id is BIGINT and the driver sends a string, some engines cast the column rather than the parameter, discarding the index for the whole table. In MySQL this is also a correctness hazard: comparing a string column to a number coerces both to floats. Match your parameter types. :::

#Finding unused and missing indexes

::: warn Every index costs writes and space Each INSERT updates every index on the table; each UPDATE updates every index containing a changed column. Ten indexes on a hot table can halve write throughput. Indexes also compete for buffer cache with the data itself.

SQL Server's "missing index" DMVs suggest wide, overlapping indexes with no awareness of what already exists — treat them as a hint to investigate, never as a script to run. :::
