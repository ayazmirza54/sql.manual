Creating

CREATE INDEX i ON t (a)Single column
CREATE INDEX i ON t (a, b, c)Composite — leading prefix rule
CREATE UNIQUE INDEX i ON t (a)Enforces uniqueness
CREATE INDEX i ON t (lower(a))Functional index
CREATE INDEX i ON t (a) WHERE b = 1Partial / filtered
CREATE INDEX i ON t (a) INCLUDE (c)Covering
CREATE INDEX CONCURRENTLYNon-blocking (PostgreSQL)

Column order

Equality columns firstWHERE a = ? AND b > ? → (a, b)
Range/sort column lastLets the range scan stay ordered
(a, b) also serves (a)Drop the redundant single-column index
(a, b) does NOT serve (b)Leading prefix only
Match ORDER BY direction(a ASC, b DESC) for that exact sort

What blocks an index

WHERE YEAR(d) = 2026Function on the column → use a range
WHERE s LIKE '%x'Leading wildcard → trigram/full-text index
WHERE id = '42'Implicit cast on the column side
WHERE a = 1 OR b = 2Different columns → two indexes or UNION ALL
Low selectivity (>20% of rows)A scan is genuinely faster
Stale statisticsRun ANALYZE / UPDATE STATISTICS

Structures

B-tree=, <, >, BETWEEN, prefix LIKE, ORDER BY
HashEquality only
GIN (PostgreSQL)Arrays, JSONB, full-text
GiST (PostgreSQL)Geometry, ranges, KNN
BRIN (PostgreSQL)Huge ordered tables, tiny index
Columnstore (SQL Server)Analytical scans
Sort/cluster keys (warehouses)No indexes — block pruning instead

Auditing

pg_stat_user_indexes WHERE idx_scan = 0Unused (PostgreSQL)
sys.schema_unused_indexesUnused (MySQL)
sys.dm_db_index_usage_statsUsage (SQL Server)
EXPLAIN (ANALYZE, BUFFERS)Did it actually get used?
