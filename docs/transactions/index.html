Transactions, isolation & locking

ACID, the four isolation levels and the anomalies they permit, MVCC vs locking, deadlocks, and the concurrency patterns that actually work.

A transaction is a unit of work that either happens completely or not at all.

EngineStartSavepointsAutocommit default
PostgreSQLBEGIN / START TRANSACTIONYesOn
MySQL / MariaDBSTART TRANSACTION / BEGINYesOn (autocommit=1)
SQL ServerBEGIN TRANSACTIONYesOn (implicit transactions optional)
OracleImplicit — a transaction starts at the first DMLYesOff — you must COMMIT
SQLiteBEGIN / BEGIN IMMEDIATEYesOn
BigQueryBEGIN TRANSACTIONNoOn
SnowflakeBEGINNoOn

::: warn DDL and transactions PostgreSQL, SQL Server, SQLite, Db2 and CockroachDB support transactional DDL — a CREATE TABLE inside a transaction rolls back. MySQL and Oracle issue an implicit COMMIT before and after every DDL statement, so a migration that fails halfway leaves the schema partially changed. :::

#ACID

PropertyGuaranteeMechanism
AtomicityAll or nothingUndo log / rollback segment
ConsistencyConstraints hold before and afterConstraint checking
IsolationConcurrent transactions do not corrupt each otherMVCC or locking
DurabilityA committed transaction survives a crashWrite-ahead log + fsync

::: note Durability is a setting, not an absolute synchronous_commit = off (PostgreSQL), innodb_flush_log_at_trx_commit = 2 (MySQL), PRAGMA synchronous = NORMAL (SQLite) all trade durability for throughput. They are legitimate choices for some workloads — provided everyone knows a crash can lose the last fraction of a second of committed transactions. :::

#Isolation levels

The standard defines four levels by which anomalies they permit.

LevelDirty readNon-repeatable readPhantom readLost update / write skew
READ UNCOMMITTEDPossiblePossiblePossiblePossible
READ COMMITTED—PossiblePossiblePossible
REPEATABLE READ——Possible*Write skew possible
SERIALIZABLE————

\* PostgreSQL's REPEATABLE READ (snapshot isolation) prevents phantom reads too — stricter than the standard requires.

#The anomalies

Dirty read — reading data another transaction has written but not committed. If that transaction rolls back, you acted on data that never existed.

Non-repeatable read — reading the same row twice in one transaction and getting different values, because another transaction committed a change in between.

Phantom read — re-running the same query returns new rows another transaction inserted.

Lost update — two transactions read a value, both compute a new one, and the second overwrites the first.

Write skew — two transactions each read an overlapping set, each check an invariant that still holds, and each write a disjoint row; together they break the invariant. Snapshot isolation permits it; only SERIALIZABLE prevents it.

::: note The classic write-skew example Two doctors are on call; the rule is "at least one must remain". Both transactions read "2 on call", both conclude it is safe to sign off, both update different rows. Nobody is on call. REPEATABLE READ will not stop this — you need SERIALIZABLE, or an explicit lock on a shared row. :::

#Defaults differ, and it matters

EngineDefault isolationImplementation
PostgreSQLREAD COMMITTEDMVCC; SERIALIZABLE uses SSI (predicate tracking, no locks)
MySQL / InnoDBREPEATABLE READMVCC + gap locks (which is how it blocks phantoms)
SQL ServerREAD COMMITTED (locking)Locks by default; READ_COMMITTED_SNAPSHOT ON switches to MVCC
OracleREAD COMMITTEDMVCC; has no REPEATABLE READ — only READ COMMITTED and SERIALIZABLE
SQLiteSERIALIZABLEOne writer at a time; WAL mode allows concurrent readers
CockroachDBSERIALIZABLEDistributed SSI
Snowflake / BigQueryREAD COMMITTEDSnapshot per statement

::: danger MySQL and SQL Server defaults surprise people moving between them MySQL defaults to REPEATABLE READ, so a long-running transaction keeps reading a stale snapshot — reports "miss" recent data. SQL Server defaults to lock-based READ COMMITTED, so readers block writers and vice versa; enabling READ_COMMITTED_SNAPSHOT usually eliminates a whole class of timeouts at the cost of tempdb version-store space. :::

#MVCC

Multi-Version Concurrency Control keeps multiple versions of each row so readers never block writers and writers never block readers.

EngineOld versions live inCleanup
PostgreSQLThe table itself (dead tuples)VACUUM / autovacuum
MySQL/InnoDBUndo tablespacePurge threads
OracleUndo tablespaceAutomatic; ORA-01555 snapshot too old if undo is recycled too soon
SQL Server (RCSI)tempdb version storeAutomatic

::: warn A long-running transaction blocks cleanup everywhere Old versions cannot be removed while any transaction might still need to see them. An idle-in-transaction session held open for hours causes PostgreSQL table bloat, InnoDB undo growth, Oracle ORA-01555 errors and SQL Server tempdb growth. Set idle_in_transaction_session_timeout and never leave a transaction open across a user interaction. :::

#Lock granularity

Row → page → table → database. Engines escalate when too many fine locks accumulate: SQL Server converts to a table lock past ~5,000 row locks, which turns a large batch update into a blocking operation for everyone. Batch your writes to stay under the threshold.

#Deadlocks

Two transactions each hold a lock the other needs. The engine detects the cycle and kills one.

Prevention:

  1. Always acquire locks in the same order — e.g. sort ids ascending before updating a batch. This alone eliminates most deadlocks.
  2. Keep transactions short; never wait on network or user input inside one.
  3. Use a single atomic statement instead of read-then-write where possible.
  4. Lower the isolation level if the workload permits it.
  5. Retry. Deadlocks are a normal condition in a busy system, not a bug — application code should catch the error (SQLSTATE 40P01 PostgreSQL, 40001 serialization failure, error 1213 MySQL, 1205 SQL Server) and retry with backoff.

#Serializable and retries

SERIALIZABLE in PostgreSQL and CockroachDB does not lock — it detects conflicts at commit time and aborts one transaction with a serialization failure. Every application using it must implement retry.

::: tip Choosing a level Start at the engine's default. Move to SERIALIZABLE for the specific transactions that enforce a cross-row invariant (booking a seat, enforcing a balance floor, allocating a unique slot) and implement retry there. Blanket SERIALIZABLE across a whole application usually costs more throughput than the correctness is worth — and blanket READ UNCOMMITTED is almost never the right answer. :::
