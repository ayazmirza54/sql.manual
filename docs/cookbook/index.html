Ranking & top-N

2

Problem. The classic interview question — and it has three correct answers depending on how you want to handle ties.

Which to use: DENSE_RANK for "the second-highest salary", ROW_NUMBER for "the second-highest-*paid person*". They give different answers as soon as two people earn the same.

::: note Dialect differences OFFSET 1 LIMIT 1 becomes OFFSET 1 ROWS FETCH NEXT 1 ROWS ONLY in SQL Server, Oracle 12c+ and Db2. Snowflake and BigQuery let you skip the subquery with QUALIFY DENSE_RANK() OVER (…) = 2. :::

Problem. One row per customer — their most recent order, with all its columns.

Why LATERAL can be much faster: with an index on (customer_id, created_at DESC) it reads exactly one index entry per customer. ROW_NUMBER sorts every order row first. On a table with millions of orders and thousands of customers, the difference is large.

::: danger Always include a tie-breaker ORDER BY created_at DESC alone is non-deterministic when two orders share a timestamp — the "latest" row can change between runs. Append the primary key. :::

::: note Dialect differences SQL Server: CROSS APPLY (SELECT TOP 1 …). MySQL 8.0.14+ supports LATERAL; earlier versions need the ROW_NUMBER form. ClickHouse has LIMIT 1 BY customer_id. :::

Time series

3

Problem. A cumulative sum down an ordered result — revenue to date, account balance, inventory position.

::: danger Say ROWS, not the default Omitting the frame gives you RANGE UNBOUNDED PRECEDING, which includes every row with the same sort key. With two rows on the same day, a RANGE running total jumps to the day's full amount on the first of them. Use ROWS for a strict row-by-row cumulative sum, or aggregate to one row per day first. :::

::: note Dialect differences Every engine with window functions supports this: PostgreSQL 8.4+, MySQL 8.0+, SQLite 3.25+, SQL Server 2012+, Oracle, and all the warehouses. On MySQL 5.7 or SQLite 3.24 you need a correlated subquery or a self-join, both O(n²). :::

Problem. Of the users who signed up in month N, how many were still active in months N+1, N+2, …?

Reading it: month_number = 0 is the cohort size (100% by definition); each subsequent row is that month's returning share. The MAX(COUNT(…)) OVER (PARTITION BY cohort_month) trick takes month 0's count as the denominator without a second query.

::: warn Incomplete periods distort the last diagonal The most recent cohort has had less time to return, and the current month is not over. Exclude periods that have not fully elapsed, or the chart will show a fake cliff at the edge. :::

::: note Dialect differences DATE_TRUNC is PostgreSQL/Snowflake/Databricks/Redshift/DuckDB. BigQuery: DATE_TRUNC(date, MONTH). MySQL: DATE_FORMAT(t, '%Y-%m-01'). SQL Server: DATETRUNC(month, t) (2022+) or DATEFROMPARTS(YEAR(t), MONTH(t), 1). Month differences: DATEDIFF(month, a, b) in SQL Server, TIMESTAMPDIFF(MONTH, a, b) in MySQL, DATE_DIFF(a, b, MONTH) in BigQuery. :::

Problem. Split a stream of user events into sessions, starting a new one after 30 minutes of inactivity.

Solution: the "gaps and islands" pattern — flag each row that starts a new session, then take a running sum of those flags as the session number.

The same three-step shape solves every "consecutive runs" problem: detect the boundary with LAG, number the groups with a running SUM, then aggregate.

::: note Dialect differences Interval arithmetic varies: TIMESTAMPDIFF(MINUTE, prev, cur) > 30 in MySQL, DATEDIFF(minute, prev, cur) > 30 in SQL Server, TIMESTAMP_DIFF(cur, prev, MINUTE) > 30 in BigQuery. Snowflake and BigQuery also have dedicated SESSIONIZE-style patterns in their docs, but this portable version works everywhere with window functions. :::

Hierarchies & graphs

1

Problem. An adjacency-list table (id, parent_id) and you need descendants, ancestors, depth or a path.

::: danger Always bound the recursion A single cyclic edge makes an unbounded recursive CTE run until it exhausts memory. PostgreSQL and SQLite impose no default limit. Add WHERE depth < n, or use the CYCLE clause (PostgreSQL 14+, Db2, Oracle). MySQL caps at cte_max_recursion_depth (1000) and SQL Server at OPTION (MAXRECURSION 100). :::

::: tip Alternatives to adjacency lists For read-heavy trees that change rarely, a materialised path (/1/17/42/, queried with LIKE '/1/17/%') or closure table (one row per ancestor-descendant pair) answers subtree queries with a single index scan and no recursion. PostgreSQL's ltree extension implements materialised paths with proper operators and GiST indexing. :::

Writes & maintenance

2

Problem. Insert without failing when the row is already there — and without a race between the check and the insert.

::: danger The check-then-insert race

Two sessions can both pass the check before either inserts. The window is microseconds, which means it will happen under load and never in testing.

The only reliable guarantee is a unique constraint. With one, either the upsert syntax handles it atomically, or the second insert raises a violation you can catch and retry. Without one, no amount of statement cleverness helps. :::

::: warn Upserts consume sequence values on conflict In PostgreSQL, INSERT … ON CONFLICT DO NOTHING still calls nextval before detecting the conflict, so a high-conflict upsert loop burns through identity values fast. This is harmless with BIGINT and worth knowing about with INT. :::

Problem. A single DELETE of 50 million rows holds locks for hours, bloats the WAL/undo, and stalls replication.

Rules for the driving loop:

  1. Commit each batch. One transaction per batch, not one for the whole job.
  2. Pause between batches (50–200 ms) so replicas, checkpoints and autovacuum catch up.
  3. Index the predicate. Without an index on created_at, every batch rescans the table and the job gets slower as it runs.
  4. Watch replication lag and back off if it grows.
  5. Keep batches under the lock-escalation threshold — SQL Server escalates to a table lock at roughly 5,000 row locks.

::: tip Partitioning turns this into an O(1) operation If the table is range-partitioned on the retention column, a year of data disappears in milliseconds:

Any table with a retention policy should be partitioned on the retention dimension from the start. :::

::: warn Deleting does not return disk space PostgreSQL leaves dead tuples for autovacuum; MySQL/InnoDB keeps the space in the tablespace. Run VACUUM / OPTIMIZE TABLE afterwards, and budget for the table temporarily needing double its size if you rebuild it. :::
