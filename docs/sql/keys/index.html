Primary keys & foreign keys

Surrogate vs natural keys, composite keys, referential actions, and the engine-specific behaviour of auto-increment.

#Primary keys

A primary key uniquely identifies each row. It implies NOT NULL + UNIQUE, and every mainstream engine backs it with an index automatically.

#Surrogate vs natural keys

Surrogate (generated id)Natural (real-world value)
StabilityNever changesChanges when the world changes (email, ISBN, VAT number)
WidthNarrow — 4/8 bytesOften wide text, inflating every secondary index
JoinsFast integer comparisonSlower string comparison, collation-sensitive
MeaningNone — needs a lookup to interpretSelf-describing
RecommendationDefault choice for OLTPAdd as a UNIQUE constraint alongside the surrogate

::: tip The usual answer Use a surrogate primary key and a UNIQUE constraint on the natural key. You get stable joins plus enforced business uniqueness. Do not rely on the surrogate alone — without the UNIQUE constraint nothing stops two rows with the same email. :::

#Auto-generated keys, per engine

This is one of the least portable areas of SQL.

::: warn Warehouses do not enforce keys Redshift, Snowflake, BigQuery, Databricks and Synapse accept PRIMARY KEY/FOREIGN KEY declarations but do not enforce them. They exist purely as optimizer hints. Duplicate rows will land silently; deduplicate in your pipeline. Redshift and Snowflake will produce wrong results from a query the optimizer rewrote assuming an unenforced uniqueness constraint you violated. :::

#Foreign keys

A foreign key requires that each non-NULL value in the referencing column exists in the referenced column, which must be a primary key or unique constraint.

#Referential actions

ActionOn delete of the parentOn update of the parent key
NO ACTIONReject — check deferred to end of statement/transactionReject
RESTRICTReject immediately, cannot be deferredReject immediately
CASCADEDelete the children tooPropagate the new value
SET NULLSet the child column to NULL (must be nullable)Same
SET DEFAULTSet the child column to its defaultSame

::: danger ON DELETE CASCADE is a loaded gun A single DELETE on a parent can silently remove millions of descendant rows across a deep tree, inside one transaction, holding locks the whole time. It is right for genuinely owned data (order → order_items) and wrong for anything a human might want back. Prefer RESTRICT plus an explicit archival step for everything else. :::

::: warn Two footguns worth memorising SQLite does not enforce foreign keys unless you run PRAGMA foreign_keys = ON; on every connection — the default is off for backwards compatibility.

Oracle has no ON UPDATE clause at all. Primary key values are expected to be immutable; propagate updates with a trigger or, better, don't update keys. :::

#Always index your foreign keys

Only PostgreSQL, SQL Server and Oracle leave the referencing column unindexed by default; MySQL/InnoDB creates one automatically. An unindexed FK column makes every parent delete or update perform a full scan of the child table, and in Oracle it escalates to a share lock on the whole child table.
