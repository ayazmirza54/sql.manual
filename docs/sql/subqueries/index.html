Subqueries

Scalar, row, table and correlated subqueries; EXISTS vs IN vs JOIN, and when each produces a better plan.

A subquery is a SELECT nested inside another statement. Four shapes, each legal in different positions:

ShapeReturnsLegal in
ScalarExactly one row, one columnSELECT list, WHERE, SET, HAVING
RowOne row, several columnsWHERE (a,b) = (SELECT …)
Table (derived table / inline view)Many rows and columnsFROM, JOIN
CorrelatedRe-evaluated per outer rowAnywhere, but conceptually a loop

#Scalar subqueries

::: warn A scalar subquery returning more than one row is a runtime error "more than one row returned by a subquery used as an expression" (PostgreSQL) / ORA-01427 (Oracle). It often only fires in production, when the data finally contains a duplicate. Guard with LIMIT 1 plus a deterministic ORDER BY, or restructure as a join. :::

A scalar subquery that returns zero rows yields NULL, not an error — a quieter and often nastier bug.

#Correlated subqueries

A correlated subquery references a column from the outer query, so it is logically re-evaluated for every outer row.

The same result as a window function, which reads the table once instead of once per row:

::: tip Modern planners often decorrelate automatically PostgreSQL, SQL Server, Oracle and DuckDB can rewrite many correlated subqueries into joins or hash aggregates. But "often" is not "always" — an EXPLAIN showing a nested loop with a subplan executed millions of times means it did not, and you should rewrite by hand. :::

#EXISTS vs IN vs JOIN

Three ways to express "customers who have ordered":

EXISTSINJOIN
Duplicates outer rowsNoNoYes — needs DISTINCT
Safe when the inner set has NULLsYesYes for IN, no for NOT INYes
Can select inner columnsNoNoYes
Typical planSemi joinSemi join (after unnesting)Hash/merge join + dedup

::: danger NOT IN with NULLs returns nothing If the subquery yields even one NULL, NOT IN can never be true. Use NOT EXISTS. Full explanation in NULL & three-valued logic. :::

SELECT 1 vs SELECT * inside EXISTS makes no difference — every engine discards the select list. Write whichever you find clearer.

#ANY / ALL / SOME

x = ANY (…) is exactly x IN (…); x <> ALL (…) is exactly x NOT IN (…) — including the NULL trap. ALL over an empty set is TRUE; ANY over an empty set is FALSE.

#Derived tables

A subquery in FROM. Most engines require an alias.

Beyond two levels of nesting, a CTE reads far better and can be reused.

#Subqueries in the SELECT list

#Restrictions worth knowing

  • MySQL cannot modify a table and select from the same table in a subquery (ERROR 1093). Wrap the subquery in another derived table to force materialization.
  • SQLite has no ALL/ANY quantifiers.
  • Redshift does not support correlated subqueries in every position — some forms raise "This type of correlated subquery pattern is not supported".
  • BigQuery requires correlated subqueries to be aggregated or EXISTS-shaped; arbitrary correlation is limited.
