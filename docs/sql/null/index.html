NULL & three-valued logic

NULL is not a value. How three-valued logic changes comparisons, aggregates, joins, uniqueness and NOT IN.

NULL marks the absence of a value — "unknown" or "not applicable". It is not zero, not an empty string, and not equal to another NULL. Every comparison involving it yields UNKNOWN, giving SQL a three-valued logic.

#The NOT IN trap

This is the single most expensive NULL bug in production SQL. If the subquery returns even one NULL, NOT IN returns no rows.

The reason: id NOT IN (1, 2, NULL) expands to id <> 1 AND id <> 2 AND id <> NULL, and that last term is UNKNOWN, so the whole conjunction can never be TRUE.

::: tip Prefer NOT EXISTS It is NULL-safe by construction, expresses the intent ("no matching row"), and PostgreSQL, SQL Server and Oracle all compile it to an anti-join. NOT IN frequently blocks that optimization. :::

#NULL in aggregates

Aggregate functions ignore NULL — except COUNT(*), which counts rows rather than values.

::: warn AVG is not what you may think AVG(bonus) divides by the number of non-NULL bonuses. If you want NULLs treated as zero, say so: AVG(COALESCE(bonus, 0)). The two produce different numbers on the same data, and both are "right" for different questions. :::

Note also that SUM over an empty or all-NULL set returns NULL, not 0. Wrap it if a number is required: COALESCE(SUM(x), 0).

::: danger Oracle: '' IS NULL Oracle treats the zero-length string as NULL for VARCHAR2. WHERE name = '' never matches, and INSERT … VALUES ('') stores a NULL. This is Oracle-specific and long-standing; no other major engine behaves this way. Migrations to and from Oracle must handle it explicitly. :::
