Schemas, catalogs & naming

Three-part naming, search paths, and what "database" and "schema" mean in each engine — they are not the same thing.

The standard defines a three-level namespace: catalog → schema → object. Engines map their own concepts onto it inconsistently, which is why a "database" in MySQL is a "schema" in PostgreSQL.

EngineCatalogSchemaCross-container query in one statement?
PostgreSQLdatabaseschema (public default)No — one database per connection (or use FDW / dblink)
MySQL / MariaDB(unused)database == schemaYes — db1.t joined to db2.t
SQL Server / Synapsedatabaseschema (dbo default)Yes — db.schema.table
Oracledatabase / PDBuser == schemaWithin a PDB; across PDBs via DB links
SQLiteattached db (main, temp)(none)Yes, after ATTACH DATABASE
SnowflakedatabaseschemaYes — db.schema.table
BigQueryprojectdatasetYes — ` project.dataset.table `
RedshiftdatabaseschemaYes (cross-database read via federated names)
DatabrickscatalogschemaYes — Unity Catalog catalog.schema.table

#Resolution: search_path and friends

Unqualified names are resolved against an ordered list of schemas.

#Identifier quoting and case

Unquoted identifiers are case-insensitive but get folded to a canonical case — and the engines disagree on which case.

EngineUnquoted folds toQuote characterQuoted is case-sensitive
PostgreSQLlower"name"Yes
Oracle, Db2, SnowflakeUPPER"NAME"Yes
SQL Serverpreserved (comparison follows the collation)[name] or "name"Depends on collation
MySQL / MariaDBpreservedbacktick-quoted name or "name" in ANSI_QUOTES modeTable names follow the filesystem; columns are case-insensitive
SQLitepreserved, compared case-insensitively"name", [name], backtick-quoted nameNo
BigQuerypreserved; datasets/tables case-sensitivebacktick-quoted project.dataset.tableYes

::: tip Use snake_case, never quote Lowercase snake_case identifiers behave identically in every engine and never require quoting. The moment one "CamelCase" name enters a schema, every tool, ORM and ad-hoc query has to quote it correctly forever. :::

#Reserved words

user, order, group, table, from, select, key, value, timestamp, level, rank and several hundred others are reserved somewhere. A name that works in MySQL may fail in PostgreSQL or Oracle.
