Sequences & identity columns

Generating unique numbers: sequences, identity columns, caching, gaps, and why sequences are not transactional.

A sequence is a schema object that hands out numbers. An identity column is a column wired to an implicit sequence. Both exist to generate surrogate keys without a race between concurrent inserts.

::: warn Sequences are not transactional, by design nextval is exempt from rollback. If a transaction consumes id 42 and then rolls back, 42 is gone forever. Gaps are normal and unavoidable — a sequence guarantees uniqueness and monotonicity, never contiguity.

If you need gapless numbering (invoice numbers in many jurisdictions), you need a counter table plus a serialised update, and you must accept the write contention that comes with it. :::

#Identity columns

GENERATED ALWAYS rejects an explicit value unless you override it, which is what you want in normal operation but painful during a data migration:

::: danger The single most common migration bug Loading rows with explicit ids and forgetting to advance the sequence. Everything works until the first natural insert, which then fails with a duplicate key error — often days later, in production. Reseed as the last step of every restore or bulk load. :::

#CACHE and the cost of a crash

CACHE n preallocates n values per session in memory. It removes a catalog write per insert (a large throughput win) at the cost of losing the unused block on crash or disconnect — bigger gaps.

Oracle's default cache is 20; PostgreSQL's is 1. Under heavy concurrent insert load in PostgreSQL, raising the cache is a real optimization; in a cluster with logical replication, remember each node caches separately.

#Distributed alternatives

A central sequence is a coordination point that does not scale across nodes or regions.

StrategySortableCoordinationNotes
UUIDv4NoNoneRandom; terrible for clustered-index locality (page splits in InnoDB/SQL Server)
UUIDv7Yes (time-ordered)NoneNow the default recommendation; PG 18 ships uuidv7(), others via extension
ULIDYesNone26-char lexicographically sortable, same idea as UUIDv7
Snowflake IDYesNode id assignment64-bit: timestamp + node + counter; fits BIGINT
unique_rowid()RoughlyNoneCockroachDB built-in; avoids the hot-range problem of sequential keys

::: warn UUIDv4 as a clustered primary key In MySQL/InnoDB and SQL Server the primary key determines physical row order. Random UUIDs scatter inserts across every page in the table, causing page splits, write amplification and a buffer pool that no longer fits the working set. Use UUIDv7/ULID, or store a BIGINT key and keep the UUID as a secondary unique column. :::
