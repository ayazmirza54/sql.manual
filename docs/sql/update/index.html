UPDATE

UPDATE with joins in each dialect, correlated updates, batching large updates, and the missing-WHERE disaster.

::: danger An UPDATE without WHERE updates every row There is no confirmation prompt. Enable SET SQL_SAFE_UPDATES = 1 in MySQL, run BEGIN; first in PostgreSQL so you can ROLLBACK, and habitually write the SELECT first, then edit it into an UPDATE. :::

#UPDATE from another table

Every engine solves this differently — one of the sharpest dialect splits in SQL.

::: warn Omitting the EXISTS guard nulls out non-matching rows In the correlated form, rows with no matching customer get NULL — the subquery returns nothing. The WHERE EXISTS clause restricts the update to rows that actually have a match. This bug is easy to miss because it looks like it worked. :::

#Batching large updates

A single UPDATE touching millions of rows holds locks for its whole duration, bloats the undo/WAL, and can stall replication. Chunk it.

::: note LIMIT on UPDATE is not portable MySQL, MariaDB and SQLite (compiled with SQLITE_ENABLE_UPDATE_DELETE_LIMIT) accept LIMIT on UPDATE. PostgreSQL, Oracle and Db2 do not — use the IN (SELECT … LIMIT n) pattern above. :::

#Rows affected

EngineHow to read the count
PostgreSQLGET DIAGNOSTICS n = ROW_COUNT in PL/pgSQL; driver-reported otherwise
MySQLROW_COUNT() — by default counts rows changed, not matched. CLIENT_FOUND_ROWS flips this
SQL Server@@ROWCOUNT
OracleSQL%ROWCOUNT
SQLitechanges()

::: warn MySQL's "0 rows affected" can mean success If the new values equal the existing ones, MySQL reports 0 changed rows even though the WHERE matched. Application code that treats 0 as "row not found" will misbehave. :::
