ORDER BY & sorting

Deterministic sorting, NULL placement, collations, custom orderings and the cost of a sort.

Without ORDER BY a result has no defined order. An unordered query that appears sorted is a coincidence of the current plan; adding an index, a parallel scan or more data changes it.

::: tip Always add a unique tie-breaker Sorting by a non-unique column leaves rows with equal keys in an arbitrary, unstable order. That silently breaks pagination: the same row can appear on page 1 and page 2. Append the primary key. :::

#Collations

Collation decides how text compares and sorts: case sensitivity, accent sensitivity, and locale rules (in Swedish 'ä' sorts after 'z'; in German it sorts with 'a').

::: warn Changing a collation invalidates indexes A B-tree index stores keys in collation order. Changing the collation of a column (or upgrading the OS's ICU/glibc version under PostgreSQL) makes existing indexes silently wrong — lookups start missing rows. After a glibc or ICU upgrade, REINDEX every text index. :::

#The cost of sorting

A sort is O(n log n) and needs memory; when it exceeds the working-memory limit the engine spills to disk, often the single largest cost in a slow query.
