Views & materialized views

Stored queries, updatable views, WITH CHECK OPTION, and the refresh strategies for materialized views in each engine.

A view is a named query. It stores no data: every reference re-executes the underlying statement, and the optimizer usually inlines it into the calling query.

Views are worth using for three reasons: they hide join complexity behind a stable name, they act as a security boundary (grant on the view, not the base tables), and they give you a compatibility layer when the physical schema has to change under a live application.

::: note Views are not a performance feature A plain view costs the same as pasting its body into your query — no more, no less. If you need the result cached, you want a materialized view or a summary table. :::

#Updatable views

The standard allows INSERT/UPDATE/DELETE through a view when the engine can map each result row unambiguously to exactly one base row: a single base table, no aggregation, no DISTINCT, no GROUP BY, no set operations, no window functions.

#Materialized views

A materialized view stores the result. Queries read the stored rows; the trade-off is staleness plus refresh cost.

EngineIncremental refreshAuto refreshQuery rewrite
PostgreSQLNo — full rebuildNo (schedule it)No
OracleYes (FAST, with MV logs)ON COMMIT / ON DEMANDYes
SQL Server (indexed view)Yes — synchronousAlwaysYes (Enterprise)
SnowflakeYes — background serviceYesYes
BigQueryYes — incrementalYes (enable_refresh)Yes
RedshiftYes (AUTO REFRESH YES)YesYes
DatabricksYes (Delta Live Tables / MVs)ScheduledLimited
ClickHouseInsert-time onlyOn insertNo
MySQL / SQLite / DuckDBNot supported — use a table + scheduled job——

::: warn "Materialized view" means five different things In Oracle and SQL Server it can be maintained transactionally; in PostgreSQL it is a manual snapshot; in ClickHouse it is an insert trigger that never sees historical rows. Read the engine's page before assuming the semantics you know carry over. :::
