Arrays & nested data

Array columns, UNNEST, aggregation back into arrays, structs and repeated fields in warehouses.

Arrays let one column hold an ordered list. PostgreSQL, BigQuery, Snowflake, DuckDB, Trino, ClickHouse and Databricks support them natively; MySQL, SQL Server, SQLite and Oracle do not (they use JSON or a child table instead).

  • ✓PostgreSQLSupported
  • ✓BigQuerySupportedARRAY
  • ✓SnowflakeSupportedARRAY of VARIANT
  • ✓DuckDBSupported
  • ✓TrinoSupported
  • ✓ClickHouseSupported

  • ⚠RedshiftDifferent syntaxSUPER type
  • ⚠OracleDifferent syntaxVARRAY/nested tables
  • ✕MySQLUnsupporteduse JSON
  • ✕SQL ServerUnsupporteduse JSON
  • ✕SQLiteUnsupporteduse JSON

::: warn Array indexes are 1-based in PostgreSQL and Oracle, 0-based in BigQuery, Trino… and both in Snowflake BigQuery makes you say which: arr[OFFSET(0)] (0-based) or arr[ORDINAL(1)] (1-based). ClickHouse, PostgreSQL and Trino are 1-based; Snowflake and DuckDB are 0- and 1-based respectively. Check before porting. :::

#Aggregating rows into an array

Where arrays are unavailable, aggregate to a delimited string instead:

EngineString aggregate
PostgreSQL, SQL Server 2017+, SQLite (as group_concat)STRING_AGG(expr, ',' ORDER BY …)
MySQL / MariaDBGROUP_CONCAT(expr ORDER BY … SEPARATOR ',')
OracleLISTAGG(expr, ',') WITHIN GROUP (ORDER BY …)
BigQuerySTRING_AGG(expr, ',' ORDER BY …)
SnowflakeLISTAGG(expr, ',') WITHIN GROUP (ORDER BY …)
ClickHousearrayStringConcat(groupArray(expr), ',')

::: warn GROUP_CONCAT truncates silently MySQL's group_concat_max_len defaults to 1024 bytes and truncates without an error. Oracle's LISTAGG raises ORA-01489 past 4000 bytes unless you use ON OVERFLOW TRUNCATE. Neither is safe for unbounded lists. :::

#Structs and repeated fields

Warehouses model nested objects with STRUCT (a record) plus ARRAY (repetition) — a schema shape that removes the need for many joins.

::: tip When to use an array instead of a child table Arrays are a good fit when the list is small, read whole, and never joined or constrained — tags, feature flags, a few labels. Anything you need to filter, index individually, count across rows, or enforce a foreign key on belongs in a child table. In warehouses the calculus flips: nested repeated fields avoid shuffles and are usually the faster design. :::
