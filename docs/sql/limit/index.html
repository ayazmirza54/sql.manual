LIMIT, OFFSET & FETCH

Row limiting in every dialect, why OFFSET pagination degrades, and how keyset pagination fixes it.

#Every dialect, one operation

::: warn LIMIT without ORDER BY is meaningless "The first 10 rows" of an unordered set is whichever 10 the plan happened to produce. SQL Server and Db2 reject OFFSET … FETCH without ORDER BY for exactly this reason; the other engines accept it and return non-deterministic results. :::

#WITH TIES

Include rows that tie with the last one, so a "top 10" can return 12 rows rather than cutting a tie arbitrarily.

  • ✓PostgreSQLSupported13+
  • ✓SQL ServerSupportedTOP n WITH TIES
  • ✓OracleSupported

  • ✕SnowflakeUnsupported

Where it is missing, use RANK():

#Why OFFSET pagination degrades

OFFSET 100000 does not skip cheaply — the engine must generate, sort and discard 100,000 rows before returning the next 10. Page 10,000 costs 1,000× page 1.

There is a correctness problem too: if a row is inserted while a user pages, every subsequent page shifts by one — rows are seen twice or skipped entirely.

#Keyset (seek) pagination

Remember the last row's sort key and ask for "the rows after it". Constant time on every page, and stable under concurrent inserts.

The matching index makes it a pure range scan:

OFFSETKeyset
Deep page costLinear in the offsetConstant
Stable under concurrent writesNoYes
Jump to page 8,347YesNo — only next/previous
Total page countEasyNeeds a separate (expensive) count

::: tip When you must show a page count Don't run COUNT(*) over the full table on every request. Cache it, use an approximate count (pg_class.reltuples, SHOW TABLE STATUS), or show "next page" affordances instead of numbered pages. Most product surfaces do not need an exact total. :::
