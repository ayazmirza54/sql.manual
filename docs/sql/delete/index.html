DELETE

DELETE with joins, deleting duplicates, soft deletes, batching, and reclaiming the space afterwards.

For emptying a whole table, TRUNCATE is dramatically faster.

#DELETE with a join

#Deleting duplicates, keeping one

#Soft deletes

Marking rows as deleted rather than removing them keeps history and makes "undo" trivial, at the cost of every query needing a filter.

::: warn Soft deletes and foreign keys do not mix cleanly A foreign key cannot express "must reference a non-deleted row". Children keep pointing at logically-deleted parents. Either enforce it in application code, or use a trigger, or accept it. :::

#Batched purge

::: tip Partition by time for anything with a retention policy Deleting a month of data from a 2-billion-row table takes hours as a DELETE and milliseconds as a partition drop. If you know in advance that data expires, partition on the expiry dimension from day one. :::

#Space is not returned automatically

EngineAfter a large DELETE
PostgreSQLRows become dead tuples. Autovacuum makes the space reusable; VACUUM FULL (exclusive lock) or pg_repack (online) returns it to the OS
MySQL/InnoDBSpace stays in the tablespace. OPTIMIZE TABLE rebuilds; with innodb_file_per_table the file shrinks
SQL ServerPages are deallocated; run ALTER INDEX … REBUILD to defragment
OracleHigh-water mark stays put; ALTER TABLE … SHRINK SPACE (needs row movement enabled)
SQLiteFreed pages are reused; VACUUM; rewrites the file, or set PRAGMA auto_vacuum
